# Agent-owned setup

Handle requested setup and authorized repairs from the installed plugin files. Merely opening a session does not start this workflow. For a Claude readiness-only request, use [session-start](../session-start/SKILL.md). Setup is prerequisite repair, not a new planning initiative. In plan/read-only mode, read sources and run doctor only; report required changes and defer mutations until execution is allowed. Installation paths are instruction sources, not the working repository; verify their origin through the native plugin list if needed.

1. Establish the actual host (Claude, Codex or Grok) and working repository from the session. Run `node <plugin-root>/scripts/setup/agent-setup.mjs doctor --client <host>` from that directory. Its `ready` result covers installation and configuration; `repositoryAdopted` separately reports repository-entry disposition. Read the separate `observer` capability result on Claude. Neither setup readiness nor a runtime version proves active observation, first-turn coverage, skill loading or authentication. Completion: exact setup gaps and runtime limitations are distinguished by the capabilities they affect.
2. When doctor reports setup gaps and the work authorizes their repair, perform `repair --client <host>` yourself using the same installed script. It installs/enables only named process companions, reuses registered marketplaces and preserves existing settings. Read any failure and inspect the actual environment. Repair missing executables through the supported CLI/package installation mechanism within current authority. For authentication or unavailable privilege, tell the human the exact required action and why only they can do it. Continue independent work; a missing Grok login holds Grok delegation, not all planning. Completion: each gap is repaired and verified, or explicitly assigned to its affected action.

   Claude repair enables the native observer experiment for future sessions. The plugin supplies the default observed MAIN agent without pinning the main model or reducing its inherited tools. Preserve an existing custom `agent` setting and report that exact conflict for a human choice. For `observer.firstInteractiveTurn: known-missing`, report the runtime limitation and continue independent work: setup repair cannot correct it. Other runtime versions remain `unverified` until first-turn coverage is demonstrated. Apply the [observer skill](../sdlc-observer/SKILL.md) when assessing runtime evidence.
3. Before adopting a repository, determine from its actual remotes, bundle source manifest and repository instructions whether it owns the canonical process sources. A canonical source owner keeps its canonical entry: identify the canonical and installed revisions and follow `<plugin-root>/SOURCE-ADAPTER.md` precedence without adding the installed-precedence marker. Otherwise use `repair --client <host> --repo <actual-repo>` when the user's work requests Sidkik SDLC there, its instructions already require this process, or an existing managed entry needs migration. This updates only a marked instruction block. Plugin installation does not replace unrelated repository policies. Preserve other repository instructions and resolve an actual conflict before changing policy. Completion: the repository retains its established canonical entry or its authorized entry points at the installed process without machine-specific source paths.
4. After repair, rerun `doctor` with the same host and repository. On a persistent failure, stop retrying unchanged commands after one corrective attempt. Show the exact remaining blocker and continue independent work; never claim ready from an install exit code alone. Reload plugins/restart the host only when its installed hook/skill definitions changed. Codex hook trust is a native human review; explain that prompt and never edit trust settings to bypass it. Completion: current verification supports the reported setup state.
5. Load the installed source adapter, `sdlc-process`, and its required `orchestrator` dependency before selecting a work route or investigating governed work. Load `sdlc-status` and write its actual session state at required events. Completion: skill source loading and criterion evidence are actual actions, not assertions inferred from installation.

For an update request, run `update --client <host>` from this installed script, then verify again using the newly installed process plugin's script path from the native plugin list. The previous runtime may remain in a versioned cache; use the current installation. No release checkout, copied credentials or manual shell checklist is required.

Separate this installed/discovered version from the actual native skill invocation
path and returned source bytes in the active session. After relevant definitions
change, follow [session-start's continuation check](../session-start/SKILL.md):
reload affected skills natively and fully read current sources and applicable
references before dependent continuation, pivot or dispatch, or report the scoped
load gap. An update or successful doctor never proves an existing session reloaded.

This workflow does not depend on a startup hook. If Node is missing, use the host's shell to inspect and repair Node first within existing authority. A CLI that is absent cannot install its own plugin; repair that CLI before retrying its native plugin commands. Keep setup results concise in terminal responses; do not create a work log or planning document merely for setup.
