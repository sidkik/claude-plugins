# Follow the work

First, load [orchestrator](../orchestrator/SKILL.md) before selecting the route or investigating the work and its evidence. **Loading a skill requires a successful native skill invocation plus a full read of its packaged source and the references it directs for the current action.** In Claude, use the `Skill` tool with the available qualified skill name. For a delegated Codex worker the native mechanism is Codex's structured skill input (`{type:"skill", name, path}`; crew: `crew-codex task --skill <name>`). Claude evidence is the `Skill` call and its success; Codex evidence is the accepted structured input and its result, never a file read. The request must resolve to exactly one enabled skill at the worker cwd, and a plugin-qualified request keeps that qualified identity through resume and redirect; a missing, disabled or ambiguous skill holds the dependent launch. Launch or discovery alone is not success: the worker's return or transcript must show the native invocation evidence and the full source and reference reads. Discovery, grep, `Read`, `cat`, and opening `SKILL.md` are source inspection, not invocation. Record the actual invocation result; a requested or failed call is not a successful load. If native invocation is unavailable or restricted (including a host without that tool), report the exact capability gap and the inspected sources separately. Source inspection can support independent authorized work, but cannot satisfy a required load or justify a readiness claim; hold only the dependent action. Completion: required invocation and source-read evidence are established, or the unmet load and its dependent action are explicit. Loading this dependency does not require spawning agents.

At continuation, a task pivot or dispatch, verify each applicable skill's loaded qualified identity, resolved path and source revision/digest against the required source or installed release under the repository's source-precedence rules. Keep the invocation evidence and comparison in the existing continuity/work record. A plugin installation update alone does not reload a skill in the current session. Reuse an earlier successful invocation and full reads when the applicable bytes remain unchanged and compatible; a newer package version alone does not require reload or restart. When relevant governing instructions changed, natively load the applicable revision and read its source and directed references before dependent work. If that revision cannot be natively loaded, report the required identity/path/revision, the actually loaded identity/path/revision and the exact capability or resolution gap. Preserve existing work and scoped human authority, hold only actions needing the changed instructions, and carry them to a fresh capable session or authorized worker with the existing continuity record. Source reads cannot substitute for that load. Completion: each applicable load is verified or its exact gap and dependent hold are explicit.

This skill connects the existing Pocock activities to the [canonical process](../../../docs/work/agent-orchestration/process/orchestration.process.md). It is the session entry procedure, not another planning methodology. Consult the [tracker configuration](../../../docs/agents/issue-tracker.md) and the process sections relevant to the current action. Reuse established context and unchanged sources; a new user turn does not restart session preparation or require rereading the entire process. For a read-only request to find the next work item, apply tracker ordering, ownership and availability checks, then report the candidate and evidence limits. Readiness/start and repair requirements become applicable when proposing or performing those actions; selecting an item alone neither requires those checks nor authorizes implementation.

## Required execution

Following the applicable process is mandatory. Establish the [route-specific stage checklist](../../../docs/work/agent-orchestration/process/orchestration.process.md#required-stage-completion) and required skill load/application results before the governed work. The entry dependency above establishes `orchestrator` before route selection or evidence investigation. Retain every required criterion, including missing evidence; phase prose and skill names cannot mark a stage complete. Update the existing work record and any status projection from criterion results, with their source revisions and assurance.

Recover omitted authorized work. If a required criterion cannot be satisfied, pause its dependent action and explain the exact blocker and needed human resolution; continue independent authorized work. Apply the canonical correction/reassessment rule before another recommendation. Ask one prerequisite-ready question at a time under the Sidkik interview adaptation; investigate technical facts yourself.

## Establish the current task

1. Read the user's desired outcome, scope and supplied sources. Locate matching work in GitHub and the owning document index before creating records. A new description need not include an issue. Discover its repository/initiative from evidence; ask only if ownership is materially ambiguous. Keep investigation moving while that answer is pending. The process's original initiative examples do not assign unrelated work to Core or its decision map.
   Starting in Core or another delivery repository is valid. Before writing a planning document, natively load [work-artifacts](../work-artifacts/SKILL.md) under the entry loading contract and read its linked [planning storage/publication convention](../../../docs/work/agent-orchestration/process/planning-repository.process.md). Establish the artifact's repository and appropriate isolated checkout through that skill even for single-repository work; cwd and existing delivery files are not placement precedent. Keep code-context work independent while any planning-checkout/publication gap is held.
2. Read the actual current issue history, candidate documents and relevant decisions, following named pointers in full. Distinguish accepted intent/design, new suggestions, current implementation and observations. Pin relevant source identities, revisions/digests, standing and gaps in the existing work record. Use OpenViking for discovery when available; retrieve canonical sources before relying on a claim. An absent context service does not prevent direct source reading.
3. Establish whether this is new work, an active continuation or a reviewed return. Check accountable ownership and existing claims. Use the [continuity procedure](../../../docs/agents/sdlc/records.md) before taking writing ownership from another session. A fresh session cannot claim a shared branch merely by finding it.
4. Name the current phase, its unresolved question and smallest authorized next action. Reuse the user's existing authorization and applicable scoped human decisions. Draft documents can support discussion, proposal writing and expressly authorized bounded work; their draft label does not erase those decisions. Record unknown authority as unknown for the affected action. Marking the whole process accepted requires its separate revision-bound adoption receipt.
   Distinguish authority to build the scoped behavior, approval to publish the specific ticket/packet, and readiness/start evidence. Trace each to its actual decision or criterion in the existing record. A missing publication approval or readiness result does not erase established build authority; build authority alone supplies neither publication approval nor readiness. Ask only for a genuinely unresolved scoped human choice.

Completion: the session can explain what this work is, which sources govern it, what remains unresolved and what action is currently justified. Do the resulting work; do not stop at presenting a route.

## Compose Pocock from the actual situation

Use [ask-matt](../../../.agents/skills/ask-matt/SKILL.md) for source inspection when needed to identify the applicable flow; inspecting a router is not executing the selected flow. Sidkik's installed workflow skills are model-invocable, so the user's ordinary request is enough: **load the selected flow yourself** with its qualified installed name (for triage on Core #546, `sdlc-process:triage` with the issue URL) under the entry loading contract, then perform it within the user's authorization and the flow's own human decisions. Do not ask the user to type a slash command, and do not read-and-follow a skill as a substitute for invocation. Loading a flow supplies its instructions only; it grants no authority, answers no human decision and permits no external write the user has not authorized. If the native tool reports that only the user can invoke a skill (a third-party or host restriction), report that exact gap with the copyable slash command using the installed qualified name and current work reference, wait for the user's invocation, hold only the dependent flow and keep the selected issue and decisions for resuming. If no valid invocation is exposed, state the missing capability rather than inventing a slash command. Completion: the selected flow has actual invocation evidence, or the exact restriction or capability gap is reported and the dependent action held.

## Advance with evidence

Before an actual advancement, use the [checkpoint boundaries](../../../docs/work/agent-orchestration/workstreams/context/governed-context.spec.md#policy-agent-checkpoints-across-the-process) to name the proposed action and obtain an independent [sdlc-policy-review](../sdlc-policy-review/SKILL.md) assessment. An ordinary question, agreement receipt, progress/blocker report or authorized correction within the current step is not a new checkpoint. A decision resolving a policy hold or changing an applicable control requires affected reassessment before dependent work. Apply the already-loaded [orchestrator](../orchestrator/SKILL.md), including its dispatch refresh rule, and use the [reviewer definition](../../../.claude/agents/sdlc-policy-reviewer.md) as its brief. Supply underlying history and exact artifacts, not just your account of compliance. Reading sources and performing already-authorized refinement or corrective work within the present step do not each create a new process transition.

Apply the process's [stage and projection boundaries](../../../docs/work/agent-orchestration/process/orchestration.process.md#required-stage-completion) when continuing from triage or updating the widget, and its [bug-intake scope](../../../docs/work/agent-orchestration/process/orchestration.process.md#bug-intake-establish-the-defect-then-preserve-redgreen) when delegating reproduction work. These distinguish investigation, status bookkeeping and actual repair execution.

Record the assessment and disposition before acting. A missing reviewer or required evidence holds the affected transition; record the unavailable capability and continue independent authorized work. Reuse a prior assessment for unchanged applicable inputs and actions it explicitly covers, with a stated basis. A bounded readiness/start or publication/integration sequence can share one assessment under the checkpoint contract; verify its outstanding conditions before each action. A reviewer cannot assess its own assessment recursively or authorize human choices. Record the accountable session's actual action and resulting state; a pass alone is not proof the action occurred.

When a checkpoint was missed, retain that omission in history and assess the next affected advancement against the actual work, current evidence and prior scoped human decisions. Preserve completed work and unchanged build authority while correcting missing evidence or briefs within the authorized step. A later assessment cannot retroactively mark the missed checkpoint passed. Name the affected hold and resume condition; obtain affected reassessment before advancing, without requesting repeated blanket build approval. A new human decision is needed only for an unresolved authority choice, changed scope/architecture or permitted exception that actually requires it.

Use the canonical [readiness and start rules](../../../docs/work/agent-orchestration/process/orchestration.process.md#readiness-and-start-rules): assess each required contract control, then separately check native order, completed blockers, current authorization and actual allocated resources. At every new selection reconsider higher work and record unavailable-item skip reasons. Reordering changes future selections only; it leaves in-flight work, including waits, intact.

For proposed or changed architecture, present a concrete proposal with alternatives, impacts and evidence for the human's revision-bound decision. Internal implementation choices remain within delegated scope. A completed preparation packet or agent endorsement supplies neither architecture approval nor permission to start.

## Continue through changes and completion

Apply [change handling](../../../docs/work/agent-orchestration/process/orchestration.process.md#revisions-and-refinement-during-work) when a source, answer or implementation changes: identify affected criteria/consumers, preserve prior evidence and pause dependent work only. Routine failures and rebasing the implementation branch onto current main are implementer repair work within accepted scope; main wins. Fundamental architecture, behavior or outside-scope changes require the revised human decision. Correct findings and repeat affected policy/QA checks before continuation.

Follow the [reporting contract](../../../docs/work/agent-orchestration/process/orchestration.process.md#human-decision-requests-and-accountable-reports) through the [shared record procedure](../../../docs/agents/sdlc/records.md). Consolidate helpers into the accountable session's return. Complete delivery only when reviewed and validated integrated main is deployable with the required evidence/dispositions. Complete [closeout](../../../docs/agents/sdlc/records.md#close-out-delivered-work), including [workspace cleanup](../../../docs/agents/sdlc/records.md#finish-triage-and-clean-up-the-workspace) and any owned local environment, in the same authorized delivery sequence and prepare its release handoff; the human controls release timing/promotion. An agent exit, merge, deployment request or green unit suite alone does not establish that completion.
