---
name: sdlc-status
description: Initialize and update the required SDLC stage checklist at session start, before governed activity, after evidence or reviews change, when corrected, and when work stops; inspect unmet criteria and human needs.
---

Read [setup and the projection contract](../../README.md) before the first update. Locate `scripts/status.mjs` relative to this installed plugin. When this plugin is available, initialization and substantive updates are required. If unavailable, present the same required criteria and unmet steps in terminal responses and name the missing display capability. The accountable agent maintains this display; the human need not construct JSON or prescribe the route.

1. Establish the actual CLI and session identity. Use Claude/Grok's current session ID, or an explicitly arranged token shared with the renderer; Codex uses that token. Completion: writer and renderer identify this session, not a repository or another agent.
2. Read the owning GitHub work, governing SDLC process, current decisions and applicable skills. Following the applicable process is mandatory. Initialize with `template --route triage|feature|delivery|research`; preserve its template, source revision and all required criteria. Select the prescribed route, not a smaller route to hide obligations. Set work, actual evidence revision, active stage, next authorized action and human need. Completion: the checklist includes the governing route and triggered skill requirements before the affected activity. For triggered specialists, add source-pinned load/application declarations before governed activity (for example `X-temporal-workflow-writer-load` and `-apply` before Temporal code). Existing declarations persist when omitted; route resets need their reviewed disposition. A template is a starting skeleton, never proof of completion.
3. Load required skills before their governed activity and record load evidence separately from application outputs. Triage's coordinated investigation requires `orchestrator` before evidence delegation planning/dispatch, including policy review. Assess conditional applicability before doing more work. An unknown conditional skill is not an instruction to invoke it. Mark N/A with a concrete reason when inapplicable; no human waiver is needed for that disposition. Later-stage requirements can remain unknown until due. Completion: each current requirement has its actual disposition; omitted results stay unknown automatically.
   For a reproduced bug proceeding to repair, report `VE-BUG1` only when the expectation is accepted, `VE-BUG2` only when a relevant-path test fails on the reported symptom (not setup/mock configuration or an unrelated failure), and `VE-BUG3` only when exact test/source, command, tested revision and expected/actual results are retained. All three passed means reproduction complete, not fixed or ready. Once these pass and no diagnostic gap remains, proceed to applicable readiness checks. If diagnosis was not needed, mark conditional `diagnosing-bugs` load/application N/A with that reason; preserve actual load/application evidence when diagnosis was needed and performed. Do not require further minimization or ranked hypotheses. `RS-BUG1` applies when actually proposing ready/start and additionally needs bounded restoration authority and applicable readiness/start controls. A disposition-only triage or requested stop/handoff records it N/A with that reason; finishing diagnosis or readiness is not a prerequisite to preserving the current state and handing off. An unresolved choice holds only dependent work. If a named diagnostic gap remains, investigate that gap; do not infer it from an unknown checkbox. Already-fixed, non-bug and specifically approved alternative-verification dispositions mark the inapplicable reproduction criteria N/A with the concrete basis; alternative evidence remains governed by existing verification and policy criteria.
4. Write JSON on stdin to `write --client CLIENT --session ID`. On each substantive event, update criterion results and their actor, evidence reference and work revision. Independent criteria also require an assessment by a distinct actor referencing that same revision. Preserve failures and unknowns. Set `activities: ["delegation"]` before attempted dispatch, `claimedComplete` when declaring a stage complete, and `active` when moving to the next stage. These explicit fields expose unmet prerequisites; free-text phase is informational. Completion: the derived stage result agrees with actual evidence, not an optimistic summary.
5. Run `inspect --client CLIENT --session ID`; reconcile every current unmet criterion. Recover authorized omissions directly. If a required step cannot be met, identify the exact criterion, blocker, dependent work held and needed human decision/capability. Continue independent authorized work. A human exception requires its actual scoped authority, conditions and alternative evidence; it remains E, never a successful performance claim.
6. After correction or relevant source/implementation change, withdraw affected passes and dependent questions/recommendations, verify the underlying flow and update the actual evidence revision. Compare against current known revisions using `--source-revision` and `--evidence-revision` when rendering/inspecting. Update only after reconciling real work; refreshing a timestamp alone does not restore evidence. Completion: affected checks are unresolved or supported by fresh evidence before dependent continuation.

Keep GitHub and the existing owning work record authoritative. The footer reports assertions; it cannot authenticate the actor, detect an unreported action, read your mind, authorize a transition or enforce the process. Missing template/capability is a visible gap, not permission to fabricate a pass. Questions and silence are not human approval. Source reads must be described as reads, not unavailable native skill invocations.
